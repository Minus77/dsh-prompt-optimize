# 模板说明

**中文** · [English](./TEMPLATES.en.md) · [Español](./TEMPLATES.es.md) · [Français](./TEMPLATES.fr.md) · [Deutsch](./TEMPLATES.de.md) · [Русский](./TEMPLATES.ru.md) · [日本語](./TEMPLATES.ja.md)

插件内置 7 个模板。它们在“提示词优化”面板右上角切换，切换只改变**改写方式**，不会改动你已经写好的草稿。

模板解决的是同一件事的不同切面：

- **基础**：先把一句话补成完整任务（任务简报、角色设定、Agent 人设）；
- **结构**：把验收标准提前，减少来回（交付契约）；
- **示范**：用例子锁住风格和格式（示例引导）；
- **推理**：要求分步执行、中途自检（推理步骤）；
- **迭代**：在已有版本上做最小改动（增量改写）。

---

## 任务简报 · Task brief

**模式**：提示词 · **分组**：基础 · **默认**

最通用的一档。适合“帮我写点什么”“帮我看看这个”这类只有目标、没有细节的草稿。

**输出结构**：目标 / 已知信息 / 交付物 / 约束 / 输出格式。信息不足的位置会留「待确认：…」，不会替你编。

**适合**

- 草稿只有一句话，但你知道自己要什么；
- 需要把口头需求变成别人也能照着做的任务；
- 想要一个能直接发送、不用再补背景的提示词。

**不适合**

- 已经有明确验收标准的长需求（用交付契约）；
- 风格要求很高、只能靠例子说清（用示例引导）。

**示例**

> 草稿：帮我写个产品发布公告，周五上线，读者是已有用户

改写后大致是：

```
目标：写一篇面向已有用户的产品发布公告，告知本周五上线的新版本。
已知信息：上线时间周五；读者是已在使用产品的老用户，不需要从零介绍产品。
交付物：一篇可直接发布的中文公告，300 字以内。
约束：不夸大功能，不承诺未上线的能力；不写价格。
输出格式：标题 + 三段正文 + 一句行动指引。
待确认：这次发布的核心功能是什么？
```

## 交付契约 · Delivery contract

**模式**：提示词 · **分组**：结构

把“什么算完成”写在前面，适合会被反复验收的任务：文档、报告、代码改动、数据整理。

**输出结构**：任务 / 输入 / 输出规格 / 验收标准（3–6 条可勾选）/ 边界与例外 / 禁止事项。

**适合**

- 结果要交给别人检查；
- 之前返工多次，原因是标准没说清；
- 需要明确“缺材料时先问，不要猜”。

**不适合**

- 探索性任务，标准本身还没定；
- 一句话就能说清的小事，写契约反而变重。

**示例**

> 草稿：把这份周报整理成一页纸，给老板看

改写后会补上：输入是哪份周报、一页纸的字段与顺序、验收标准（结论在前、每项有数据、无未解释缩写）、超出长度时怎么处理。

## 示例引导 · Worked examples

**模式**：提示词 · **分组**：示范

当“说清楚”不如“给两个例子”时用。模型对格式的模仿能力远强于对形容词的理解。

**输出结构**：任务与适用范围 → 2–3 组「输入 → 期望输出」→ 示例之外的规则 → 免责说明（示例为示意，可替换）。

**适合**

- 输出格式很讲究：表格列、文案语气、代码风格；
- 你已经有两三个“就照这样写”的样本；
- 需要覆盖不同情况，而不是重复同一个例子。

**不适合**

- 草稿里没有可参考的样本，硬造例子会误导；
- 任务本身是开放的创意工作。

---

## 推理步骤 · Reasoning steps

**模式**：提示词 · **分组**：推理

把任务拆成可执行步骤，并规定在哪一步之后自检、发现问题退回哪里。

**输出结构**：目标复述 → 3–7 个步骤（输入 / 动作 / 完成标志）→ 自检点 → 异常处理 → 交付格式。

**适合**

- 多步分析、排查、对比选型；
- 中间结果需要人工确认再继续；
- 之前出现过“一口气跑完，方向错了全废”。

**不适合**

- 单步任务；
- 需要模型自由发挥的创作。

## 角色设定 · Role contract

**模式**：系统提示词 · **分组**：基础

把一句角色设想写成智能体能长期执行的系统提示词。界面暂未暴露系统提示词模式，可经由 `POST /prompt-optimize/optimize` 的 `optimizationMode: "system"` 使用。

**输出结构**：身份 / 职责 / 工作流程 / 边界 / 输出约定。

**适合**

- 要在多个会话里复用同一个角色；
- 角色需要判断标准，而不只是头衔。

**不适合**

- 一次性的任务型提示词。

---

## Agent 人设 · Agent persona

**模式**：系统提示词 · **分组**：基础

写成一份读起来像人的文件：说话方式、判断原则、会主动做什么、不会做什么，最后给一句示例回应。

**适合**

- 助手要有稳定的语气和性格；
- 需要区分“人格”与“岗位说明”。

**不适合**

- 需要严格合规话术的场景，人格描述会干扰。

---

## 增量改写 · Incremental edit

**模式**：迭代 · **分组**：迭代

在上一版结果上按一句修改意见做最小改动：只动你指出的部分，其余逐字保留。

**输出结构**：完整提示词（不是 diff）。修改意见与原文冲突时以意见为准。

**适合**

- 大体满意，只想调语气、长度、某一段；
- 想把“再正式一点”这种模糊意见落到具体位置。

**不适合**

- 方向整体不对——重新跑一次比逐句改更快。

**示例**

> 修改意见：语气更轻松一点，把待确认的长列表收成三行

结果只改语气相关措辞和那一段列表，标题层级、标点和其余段落保持不变。

## 怎么选

| 你的情况 | 选它 |
| --- | --- |
| 只有一句话，想变成完整任务 | 任务简报 |
| 要交给别人验收 | 交付契约 |
| 有现成样例，怕格式跑偏 | 示例引导 |
| 多步任务，怕中途跑歪 | 推理步骤 |
| 大体满意，只想小改 | 增量改写 |

模板不是越多越好：同一段草稿换模板会得到明显不同的结构，建议先固定一个常用模板，再在需要时切换。
