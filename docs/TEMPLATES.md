# 模板说明

**中文** · [English](./TEMPLATES.en.md) · [Español](./TEMPLATES.es.md) · [Français](./TEMPLATES.fr.md) · [Deutsch](./TEMPLATES.de.md) · [Русский](./TEMPLATES.ru.md) · [日本語](./TEMPLATES.ja.md) · [Português (BR)](./TEMPLATES.pt.md)

插件内置 15 个模板。它们在“提示词优化”面板右上角切换，切换只改变**改写方式**，不会改动你已经写好的草稿。

模板解决的是同一件事的不同切面：

- **基础**：先把一句话补成完整任务（任务简报、角色设定、Agent 人设）；
- **结构**：把验收标准或目标 schema 提前，减少来回（交付契约、结构化抽取）；
- **示范**：用例子锁住风格和格式（示例引导）；
- **推理**：要求分步执行、中途自检，或只依据给定资料回答（推理步骤、资料问答）；
- **工程**：代码审阅、实现任务、SQL、测试设计四类日常工程请求；
- **写作**：翻译本地化和润色，重点在「允许改到哪一层」；
- **迭代**：在已有版本上做最小改动（增量改写）。

菜单最后一项可以新建**自定义模板**：自己写改写要求，只保存在本机浏览器，支持 JSON 导入导出。

## 任务简报 · Task brief

**模式**：提示词 · **分组**：基础 · **默认**

最通用的一档。适合“帮我写点什么”“帮我看看这个”这类只有目标、没有细节的草稿。

**输出结构**：目标 / 已知信息 / 交付物 / 约束 / 输出格式。信息不足的位置会留「待确认：…」，不会替你编。

**适合**

- 草稿只有一句话，但你知道自己要什么；
- 需要把口头需求变成别人也能照着做的任务；
- 想要一个能直接发送、不用再补背景的提示词。

**不适合**

- 已经有明确验收标准的长需求（用交付契约）；
- 风格要求很高、只能靠例子说清（用示例引导）。

**示例**

> 草稿：帮我写个产品发布公告，周五上线，读者是已有用户

改写后大致是：

```
目标：写一篇面向已有用户的产品发布公告，告知本周五上线的新版本。
已知信息：上线时间周五；读者是已在使用产品的老用户，不需要从零介绍产品。
交付物：一篇可直接发布的中文公告，300 字以内。
约束：不夸大功能，不承诺未上线的能力；不写价格。
输出格式：标题 + 三段正文 + 一句行动指引。
待确认：这次发布的核心功能是什么？
```

## 交付契约 · Delivery contract

**模式**：提示词 · **分组**：结构

把“什么算完成”写在前面，适合会被反复验收的任务：文档、报告、代码改动、数据整理。

**输出结构**：任务 / 输入 / 输出规格 / 验收标准（3–6 条可勾选）/ 边界与例外 / 禁止事项。

**适合**

- 结果要交给别人检查；
- 之前返工多次，原因是标准没说清；
- 需要明确“缺材料时先问，不要猜”。

**不适合**

- 探索性任务，标准本身还没定；
- 一句话就能说清的小事，写契约反而变重。

**示例**

> 草稿：把这份周报整理成一页纸，给老板看

改写后会补上：输入是哪份周报、一页纸的字段与顺序、验收标准（结论在前、每项有数据、无未解释缩写）、超出长度时怎么处理。

## 示例引导 · Worked examples

**模式**：提示词 · **分组**：示范

当“说清楚”不如“给两个例子”时用。模型对格式的模仿能力远强于对形容词的理解。

**输出结构**：任务与适用范围 → 2–3 组「输入 → 期望输出」→ 示例之外的规则 → 免责说明（示例为示意，可替换）。

**适合**

- 输出格式很讲究：表格列、文案语气、代码风格；
- 你已经有两三个“就照这样写”的样本；
- 需要覆盖不同情况，而不是重复同一个例子。

**不适合**

- 草稿里没有可参考的样本，硬造例子会误导；
- 任务本身是开放的创意工作。

## 推理步骤 · Reasoning steps

**模式**：提示词 · **分组**：推理

把任务拆成可执行步骤，并规定在哪一步之后自检、发现问题退回哪里。

**输出结构**：目标复述 → 3–7 个步骤（输入 / 动作 / 完成标志）→ 自检点 → 异常处理 → 交付格式。

**适合**

- 多步分析、排查、对比选型；
- 中间结果需要人工确认再继续；
- 之前出现过“一口气跑完，方向错了全废”。

**不适合**

- 单步任务；
- 需要模型自由发挥的创作。

## 角色设定 · Role contract

**模式**：系统提示词 · **分组**：基础

把一句角色设想写成智能体能长期执行的系统提示词。界面暂未暴露系统提示词模式，可经由 `POST /prompt-optimize/optimize` 的 `optimizationMode: "system"` 使用。

**输出结构**：身份 / 职责 / 工作流程 / 边界 / 输出约定。

**适合**

- 要在多个会话里复用同一个角色；
- 角色需要判断标准，而不只是头衔。

**不适合**

- 一次性的任务型提示词。

## Agent 人设 · Agent persona

**模式**：系统提示词 · **分组**：基础

写成一份读起来像人的文件：说话方式、判断原则、会主动做什么、不会做什么，最后给一句示例回应。

**适合**

- 助手要有稳定的语气和性格；
- 需要区分“人格”与“岗位说明”。

**不适合**

- 需要严格合规话术的场景，人格描述会干扰。

## 增量改写 · Incremental edit

**模式**：迭代 · **分组**：迭代

在上一版结果上按一句修改意见做最小改动：只动你指出的部分，其余逐字保留。

**输出结构**：完整提示词（不是 diff）。修改意见与原文冲突时以意见为准。

**适合**

- 大体满意，只想调语气、长度、某一段；
- 想把“再正式一点”这种模糊意见落到具体位置。

**不适合**

- 方向整体不对——重新跑一次比逐句改更快。

**示例**

> 修改意见：语气更轻松一点，把待确认的长列表收成三行

结果只改语气相关措辞和那一段列表，标题层级、标点和其余段落保持不变。

## 代码审阅 · Code review

**模式**：提示词 · **分组**：工程

把「帮我看看这段代码」变成一次有范围、有优先级的审阅。关键差异是：先说清这次改动想干什么，再规定关注点的顺序，最后约束输出格式，避免得到一堆平均用力的风格意见。

**输出结构**：审阅范围 / 关注点（按优先级）/ 输出格式（严重度、位置、问题、影响、建议）/ 不做什么 / 依据要求。

**适合**

- 提交前自审，或请别人 review 一个 PR；
- 改动跨多个文件，担心漏掉调用方；
- 想要可讨论的具体意见，而不是「建议重构」。

**不适合**

- 只想让人解释一段代码在做什么（用任务简报）；
- 需要直接改好代码（用实现任务）。

**示例**

> 草稿：帮我看看这段代码有没有问题

改写后大致是：

```
审阅范围：本次 PR 改动的 3 个文件，目的是给下单接口加上幂等校验。
关注点（按优先级）：正确性（重复请求是否真的只下一次单）＞ 并发安全 ＞ 性能 ＞ 可读性。
输出格式：按严重度分组，每条给文件:行号、问题、可能影响、具体改法。
不做：不重写整个文件，不评论命名偏好，不猜未提供的上游调用。
依据：每条结论引用具体行或调用链。
```

## 实现任务 · Implementation task

**模式**：提示词 · **分组**：工程

把编码需求补成工程说明：目标与验收、技术约束、接口契约、边界与失败处理、交付形式。它产出的是**任务说明**，不是实现代码。

**输出结构**：目标与验收 / 技术约束 / 接口契约 / 边界与失败 / 交付形式 / 待确认。

**适合**

- 交给智能体或同事实现一个中等大小的改动；
- 需求一句话，但你知道验收标准；
- 改公共模块，必须先约定接口。

**不适合**

- 探索性原型，边写边定方案；
- 需求还没想清楚，只想先看几种做法（先聊方案）。

**示例**

> 草稿：把导出功能改成异步任务，别卡住请求

改写后会写清：导出的触发接口、任务状态字段、轮询或回调方式、并发上限、失败重试与超时、权限校验、前端如何提示进度，以及哪些现有调用方必须一起改。

## SQL 查询 · SQL query

**模式**：提示词 · **分组**：工程

把一句取数需求写成口径、字段、性能约束都明确的查询任务，并要求把假设单独列出来。

**输出结构**：库表字段 / 口径（时间、去重、NULL、单位）/ 结果要求（列名、排序、粒度）/ 性能约束 / 权限与副作用 / 假设清单。

**适合**

- 报表、看板、临时分析取数；
- 口径容易有歧义（活跃、留存、GMV）；
- 大表查询，需要提前说明索引和扫描范围。

**不适合**

- 只是让你解释一条现成 SQL；
- 需要改表结构或写迁移脚本。

**示例**

> 草稿：查一下上周每个渠道的新增用户数

改写后会补齐：新用户的定义（首次注册还是首次下单）、渠道字段与去重键、时区与「上周」的起止、是否含测试账号、结果按渠道排序，以及允许的扫描范围和索引。

## 测试设计 · Test design

**模式**：提示词 · **分组**：工程

把测试需求写成用例表，覆盖正常、边界、异常与权限，并标出优先级和适合先自动化的部分。

**输出结构**：被测对象与风险 / 用例表（编号、前置、步骤、期望）/ 覆盖维度 / 优先级 / 自动化建议。

**适合**

- 新功能上线前补用例；
- 修完 bug 想确认没有回归；
- 需要给不熟悉背景的人一份可执行的清单。

**不适合**

- 直接要自动化脚本（草稿里明确要求时才写）；
- 只想知道某一条路径为什么失败。

**示例**

> 草稿：帮我给登录功能写测试用例

改写后会明确：账号密码、短信、第三方登录分别覆盖；密码错误次数锁定；空值、超长、特殊字符；未验证邮箱；权限不同角色的可见差异；并给出用例编号与优先级。

## 结构化抽取 · Structured extraction

**模式**：提示词 · **分组**：结构

把「从这段里取几个字段」写成带 schema 与缺失规则的抽取任务，输出严格 JSON。

**输出结构**：输入形态 / 目标 schema（字段、类型、必填、枚举）/ 缺失与冲突规则 / 只输出 JSON / 一个示例。

**适合**

- 把合同、邮件、工单、网页转成结构化数据；
- 需要批量跑、结果要能直接入库；
- 字段缺失时希望留空而不是猜。

**不适合**

- 需要主观总结或改写内容；
- 输入是一张需要 OCR 的图片。

**示例**

> 草稿：从这些邮件里提取公司名、联系人和金额

改写后会定义：公司名取正文还是签名、联系人是否含职位、金额的币种与是否含税、多个金额时取哪个、找不到填 null，并要求只输出 JSON。

## 翻译本地化 · Translation

**模式**：提示词 · **分组**：写作

把翻译需求写成带受众、术语表和格式约束的本地化任务。重点是「哪些不能动」：品牌名、字段名、占位符、Markdown 结构。

**输出结构**：语言与地区 / 受众与语气 / 术语表 / 格式要求 / 禁止增删。

**适合**

- 产品文案、帮助文档、邮件翻译；
- 面向特定地区，需要改写而不只是直译；
- 文本里带 `{{变量}}`、代码块或链接。

**不适合**

- 需要母语审校的正式法律文本（仍需人工）；
- 只翻一个词或一句短口令。

**示例**

> 草稿：把这段翻成日语，给客户看的

改写后会写明：面向日本企业客户的商务书面语；保留产品名与 `{{user_name}}`；保留 Markdown 标题层级和列表；不增删信息，只输出译文。

## 写作润色 · Copy polish

**模式**：提示词 · **分组**：写作

把润色需求写成明确的修订任务：允许改到哪一层、必须保留什么、禁止扩写。避免模型顺手加观点、加例子、把短文写长。

**输出结构**：文体与读者 / 允许改动层级 / 必须保留 / 禁止事项 / 输出全文 + 三条改动说明。

**适合**

- 草稿事实没问题，只是读起来不顺；
- 对外文案需要统一语气；
- 想控制在「只改词句」，不重组结构。

**不适合**

- 内容本身缺论证，需要重写；
- 方向要变（换角度、换受众）。

**示例**

> 草稿：把这段话改得正式一点

改写后会问清：正式到什么程度（对外公告还是内部邮件）、能否调整段落顺序、哪些数字和结论必须原样保留、是否允许合并句子，并要求末尾列出主要改动。

## 资料问答 · Grounded Q&A

**模式**：提示词 · **分组**：推理

把「根据这些资料回答」写成带引用与未覆盖声明的问答任务，资料冲突时要求列出来源再判断。

**输出结构**：资料范围 / 引用要求 / 未覆盖声明 / 冲突处理 / 输出结构（结论、依据、未覆盖）。

**适合**

- 基于文档、政策、合同回答问题；
- 需要对答案负责、能追溯到出处；
- 资料之间可能互相矛盾。

**不适合**

- 没有资料，只靠常识回答；
- 需要创意写作或开放式讨论。

**示例**

> 草稿：根据这份员工手册回答年假怎么算

改写后会限定：只使用手册内容，引用条款编号；手册没写的（例如离职折算）直接说未覆盖；如果手册与补充通知冲突，先列两处原文，再给判断。

## 自定义模板

模板菜单最后一项是「新建自定义模板」，填三项：

| 字段 | 作用 |
| --- | --- |
| 名称 | 菜单里显示的名字，最多 40 字 |
| 改写要求 | 你希望模型怎么改，最多 2000 字 |
| 适用对象 | 一句话说明什么草稿适合用它，可留空 |

自定义模板只存在这台浏览器的 `localStorage`，随浏览器数据一起清除；换机器或分享给同事时，用编辑器里的「导出 JSON」和「导入 JSON」。

## 怎么选

| 你的情况 | 选它 |
| --- | --- |
| 只有一句话，想变成完整任务 | 任务简报 |
| 要交给别人验收 | 交付契约 |
| 有现成样例，怕格式跑偏 | 示例引导 |
| 多步任务，怕中途跑歪 | 推理步骤 |
| 要审一段代码或一个 PR | 代码审阅 |
| 让别人实现一个改动 | 实现任务 |
| 写 SQL 取数，口径容易歧义 | SQL 查询 |
| 给功能补测试用例 | 测试设计 |
| 把材料转成固定字段 | 结构化抽取 |
| 翻译或本地化一段文案 | 翻译本地化 |
| 文字没问题，只是读起来不顺 | 写作润色 |
| 基于给定资料回答 | 资料问答 |
| 大体满意，只想小改 | 增量改写 |

模板不是越多越好：同一段草稿换模板会得到明显不同的结构，建议先固定一个常用模板，再在需要时切换。
