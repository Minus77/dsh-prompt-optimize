# テンプレート

[中文](./TEMPLATES.md) · [English](./TEMPLATES.en.md) · [Español](./TEMPLATES.es.md) · [Français](./TEMPLATES.fr.md) · [Deutsch](./TEMPLATES.de.md) · [Русский](./TEMPLATES.ru.md) · **日本語**

このプラグインには7個のテンプレートが組み込まれています。テンプレートは最適化パネルの右上で切り替えます。切り替えが変えるのは**下書きの書き換え方**だけで、下書きそのものには触れません。

どのテンプレートも、同じ問題の異なる側面を扱います。

- **Basic** — 一文を完全なタスクに変えます（task brief、role contract、agent persona）。
- **Structure** — 受け入れ基準を先頭に移します（delivery contract）。
- **Examples** — サンプルでスタイルと書式を固定します（worked examples）。
- **Reasoning** — チェックポイントを挟んだ段階的な実行を強制します（reasoning steps）。
- **Iterate** — 既存のバージョンに対する最小限の編集です（incremental edit）。

---

## Task brief

**モード**: prompt · **グループ**: basic · **既定**

汎用の選択肢です。目標だけがあって細部がない下書きに向いています（例:「何か書いて」「これを見て」）。

**出力の形**: 目標 / 既知の情報 / 成果物 / 制約 / 出力形式。情報が足りない箇所は、事実をでっち上げずに `待确认：…`（確認待ち）として残します。

**向いている場合**

- 下書きは一文だけでも、欲しいものが分かっています。
- 口頭の依頼を、他の人がそのまま実行できる形にする必要があります。
- 背景を手で補わずに、そのまま送れるプロンプトが欲しいときです。

**向かない場合**

- 要件に厳しい受け入れ基準がすでにあります（delivery contract を使います）。
- 構造よりもスタイルが重要で、例でしか伝えられない場合です（worked examples を使います）。

**例**

> 下書き: 金曜日に出す新バージョンの告知文を、既存ユーザー向けに書いて

おおよそ次のようになります。

```
Goal: a launch announcement for existing users about the release shipping this Friday.
Known: ships Friday; readers already use the product, so no from-scratch intro.
Deliverable: publishable Chinese note, under 300 characters.
Constraints: no overclaiming, no promises about unreleased features, no pricing.
Format: headline + three paragraphs + one call to action.
To confirm: what is the headline feature of this release?
```

## Delivery contract

**モード**: prompt · **グループ**: structure

「何をもって完了とするか」を先頭に置きます。ドキュメント、レポート、コードの変更、データ整理のように、繰り返しレビューされる作業に向いています。

**出力の形**: タスク / 入力 / 出力仕様 / 受け入れ基準（確認できる3〜6項目）/ 境界と例外 / 禁止事項。

**向いている場合**

- 結果を他の人が確認します。
- これまでの試行が、基準を明文化していなかったせいで差し戻されました。
- 材料が足りないときは、推測せずにモデルから質問してほしいです。

**向かない場合**

- 探索的なタスクで、基準そのものがまだ決まっていません。
- 一行の依頼で足ります。契約を足すと重くなるだけです。

**例**

> 下書き: この週報を、上司向けの1枚資料にまとめて

書き換えでは、どの週報が入力なのか、1枚資料の項目と順序、受け入れ基準（結論が先、主張には必ず数字を添える、説明のない略語を使わない）、長くなった場合の扱いが補われます。

## Worked examples

**モード**: prompt · **グループ**: examples

形容詞を並べた段落より、例を2つ出したほうが伝わる場面に使います。モデルは「プロっぽくして」を解釈するより、書式を模倣するほうがはるかに得意です。

**出力の形**: タスクと適用範囲 → 2〜3組の「入力 → 期待する出力」→ 例の外にある入力の扱い → サンプルはあくまで例示であるという注記。

**向いている場合**

- 書式が厳密です（表の列、文体、コードスタイル）。
- 「こう書いてほしい」というサンプルがすでに2〜3個あります。
- 同じケースを繰り返すより、網羅性が重要です。

**向かない場合**

- 下書きにサンプルの元になる材料がありません。でっち上げた例は誤解を招きます。
- 仕事が自由な創作です。

## Reasoning steps

**モード**: prompt · **グループ**: reasoning

タスクを実行できる手順に分解し、どこで自己チェックし、どこまで戻るかを明示します。

**出力の形**: 目標の言い直し → 3〜7個の手順（入力 / 行動 / 完了の合図）→ チェックポイント → 失敗時の処理 → 納品形式。

**向いている場合**

- 複数の手順を要する分析、デバッグ、選択肢の比較です。
- 途中の結果に人の確認が必要です。
- 以前、最後まで進んでから方針が違っていたと分かったことがあります。

**向かない場合**

- 手順が1つで終わるタスクです。
- 自由な発想が要る作業です。

## Role contract

**モード**: system prompt · **グループ**: basic

一行の役割の説明を、エージェントが長期にわたって従えるシステムプロンプトに変えます。パネルからはまだシステムプロンプトモードを使えません。`POST /prompt-optimize/optimize` に `optimizationMode: "system"` を指定して使います。

**出力の形**: アイデンティティ / 責務 / ワークフロー / 境界 / 出力の取り決め。

**向いている場合**

- 同じ役割を複数のセッションで使い回します。
- 役割に、肩書きだけでなく判断基準が要ります。

**向かない場合**

- 一度きりのタスク用プロンプトが欲しいときです。

## Agent persona

**モード**: system prompt · **グループ**: basic

人として読める文書を書きます。話し方、判断のしかた、自分から進んでやること、決してやらないことに加えて、返答の例を1つ含めます。

**向いている場合**

- アシスタントに安定した語り口と性格が要ります。
- 職務記述書ではなく人格が欲しいときです。

**向かない場合**

- コンプライアンス上の文言を厳密に保つ必要があり、人格の記述が邪魔になります。

## Incremental edit

**モード**: iterate · **グループ**: iterate

直前の結果に変更メモを1つ適用し、動かす範囲を最小にします。触れた箇所だけが変わり、それ以外はそのまま残ります。

**出力の形**: 完全なプロンプト（diffではありません）。メモと本文が衝突する場合は、メモを優先します。

**向いている場合**

- 結果はほぼ正しく、トーン、長さ、1つの段落だけを調整したいときです。
- 「もっと正式にして」のような曖昧なメモを、具体的な箇所に落とし込みたいときです。

**向かない場合**

- 方向そのものが違います。一文ずつ直すより、新しく実行したほうが速いです。

**例**

> メモ: トーンを軽く、長い「確認待ち」のリストは3行にまとめる

トーンに関わる言い回しとそのリストだけが変わり、見出し、句読点、その他の部分は同一のままです。

## 選び方

| 状況 | テンプレート |
| --- | --- |
| 一文しかないが、完全なタスクにしたい | Task brief |
| 結果を他の人が受け入れる | Delivery contract |
| サンプルはあるが、書式が崩れるのが怖い | Worked examples |
| 多段の作業で、途中で迷いやすい | Reasoning steps |
| ほぼ満足で、少しだけ直したい | Incremental edit |

テンプレートは多ければよいというものではありません。同じ下書きでも、テンプレートを変えれば構造は目に見えて変わります。常用するものを1つ決めておき、仕事の性質が変わったときだけ切り替えてください。
