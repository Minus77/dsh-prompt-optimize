# テンプレート

[中文](./TEMPLATES.md) · [English](./TEMPLATES.en.md) · [Español](./TEMPLATES.es.md) · [Français](./TEMPLATES.fr.md) · [Deutsch](./TEMPLATES.de.md) · [Русский](./TEMPLATES.ru.md) · **日本語**

このプラグインには15個のテンプレートが組み込まれています。テンプレートは最適化パネルの右上で切り替えます。切り替えが変えるのは**下書きの書き換え方**だけで、下書きそのものには触れません。

どのテンプレートも、同じ問題の異なる側面を扱います。

- **Basic** — 一文を完全なタスクに変えます（task brief、role contract、agent persona）。
- **Structure** — 受け入れ基準を先頭に移します（delivery contract）。
- **Examples** — サンプルでスタイルと書式を固定します（worked examples）。
- **Reasoning** — チェックポイントを挟んだ段階的な実行を強制します（reasoning steps）。
- **Iterate** — 既存のバージョンに対する最小限の編集です（incremental edit）。
- **Engineering** — コードレビュー、実装タスク、SQL、テスト設計という日常の開発依頼です。
- **Writing** — 翻訳・ローカライズと推敲。「どこまで変えてよいか」を先に決めます。

メニューの最後の項目から**自作テンプレート**を作れます。書き換えの指示を自分で書き、このブラウザにだけ保存されます（JSON で書き出し・読み込み可）。

## Task brief

**モード**: prompt · **グループ**: basic · **既定**

汎用の選択肢です。目標だけがあって細部がない下書きに向いています（例:「何か書いて」「これを見て」）。

**出力の形**: 目標 / 既知の情報 / 成果物 / 制約 / 出力形式。情報が足りない箇所は、事実をでっち上げずに `待确认：…`（確認待ち）として残します。

**向いている場合**

- 下書きは一文だけでも、欲しいものが分かっています。
- 口頭の依頼を、他の人がそのまま実行できる形にする必要があります。
- 背景を手で補わずに、そのまま送れるプロンプトが欲しいときです。

**向かない場合**

- 要件に厳しい受け入れ基準がすでにあります（delivery contract を使います）。
- 構造よりもスタイルが重要で、例でしか伝えられない場合です（worked examples を使います）。

**例**

> 下書き: 金曜日に出す新バージョンの告知文を、既存ユーザー向けに書いて

おおよそ次のようになります。

```
Goal: a launch announcement for existing users about the release shipping this Friday.
Known: ships Friday; readers already use the product, so no from-scratch intro.
Deliverable: publishable Chinese note, under 300 characters.
Constraints: no overclaiming, no promises about unreleased features, no pricing.
Format: headline + three paragraphs + one call to action.
To confirm: what is the headline feature of this release?
```

## Delivery contract

**モード**: prompt · **グループ**: structure

「何をもって完了とするか」を先頭に置きます。ドキュメント、レポート、コードの変更、データ整理のように、繰り返しレビューされる作業に向いています。

**出力の形**: タスク / 入力 / 出力仕様 / 受け入れ基準（確認できる3〜6項目）/ 境界と例外 / 禁止事項。

**向いている場合**

- 結果を他の人が確認します。
- これまでの試行が、基準を明文化していなかったせいで差し戻されました。
- 材料が足りないときは、推測せずにモデルから質問してほしいです。

**向かない場合**

- 探索的なタスクで、基準そのものがまだ決まっていません。
- 一行の依頼で足ります。契約を足すと重くなるだけです。

**例**

> 下書き: この週報を、上司向けの1枚資料にまとめて

書き換えでは、どの週報が入力なのか、1枚資料の項目と順序、受け入れ基準（結論が先、主張には必ず数字を添える、説明のない略語を使わない）、長くなった場合の扱いが補われます。

## Worked examples

**モード**: prompt · **グループ**: examples

形容詞を並べた段落より、例を2つ出したほうが伝わる場面に使います。モデルは「プロっぽくして」を解釈するより、書式を模倣するほうがはるかに得意です。

**出力の形**: タスクと適用範囲 → 2〜3組の「入力 → 期待する出力」→ 例の外にある入力の扱い → サンプルはあくまで例示であるという注記。

**向いている場合**

- 書式が厳密です（表の列、文体、コードスタイル）。
- 「こう書いてほしい」というサンプルがすでに2〜3個あります。
- 同じケースを繰り返すより、網羅性が重要です。

**向かない場合**

- 下書きにサンプルの元になる材料がありません。でっち上げた例は誤解を招きます。
- 仕事が自由な創作です。

## Reasoning steps

**モード**: prompt · **グループ**: reasoning

タスクを実行できる手順に分解し、どこで自己チェックし、どこまで戻るかを明示します。

**出力の形**: 目標の言い直し → 3〜7個の手順（入力 / 行動 / 完了の合図）→ チェックポイント → 失敗時の処理 → 納品形式。

**向いている場合**

- 複数の手順を要する分析、デバッグ、選択肢の比較です。
- 途中の結果に人の確認が必要です。
- 以前、最後まで進んでから方針が違っていたと分かったことがあります。

**向かない場合**

- 手順が1つで終わるタスクです。
- 自由な発想が要る作業です。

## Role contract

**モード**: system prompt · **グループ**: basic

一行の役割の説明を、エージェントが長期にわたって従えるシステムプロンプトに変えます。パネルからはまだシステムプロンプトモードを使えません。`POST /prompt-optimize/optimize` に `optimizationMode: "system"` を指定して使います。

**出力の形**: アイデンティティ / 責務 / ワークフロー / 境界 / 出力の取り決め。

**向いている場合**

- 同じ役割を複数のセッションで使い回します。
- 役割に、肩書きだけでなく判断基準が要ります。

**向かない場合**

- 一度きりのタスク用プロンプトが欲しいときです。

---

## Agent persona

**モード**: system prompt · **グループ**: basic

人として読める文書を書きます。話し方、判断のしかた、自分から進んでやること、決してやらないことに加えて、返答の例を1つ含めます。

**向いている場合**

- アシスタントに安定した語り口と性格が要ります。
- 職務記述書ではなく人格が欲しいときです。

**向かない場合**

- コンプライアンス上の文言を厳密に保つ必要があり、人格の記述が邪魔になります。

## Incremental edit

**モード**: iterate · **グループ**: iterate

直前の結果に変更メモを1つ適用し、動かす範囲を最小にします。触れた箇所だけが変わり、それ以外はそのまま残ります。

**出力の形**: 完全なプロンプト（diffではありません）。メモと本文が衝突する場合は、メモを優先します。

**向いている場合**

- 結果はほぼ正しく、トーン、長さ、1つの段落だけを調整したいときです。
- 「もっと正式にして」のような曖昧なメモを、具体的な箇所に落とし込みたいときです。

**向かない場合**

- 方向そのものが違います。一文ずつ直すより、新しく実行したほうが速いです。

**例**

> メモ: トーンを軽く、長い「確認待ち」のリストは3行にまとめる

トーンに関わる言い回しとそのリストだけが変わり、見出し、句読点、その他の部分は同一のままです。

## Code review

**モード**: prompt · **グループ**: engineering

「このコードを見て」を、範囲と優先順位のあるレビュー依頼に変えます。まず変更の目的を書き、次に観点の順番を決め、最後に出力形式を縛ります。

**出力の形**: レビュー範囲 / 観点（優先順）/ 出力形式（重大度・位置・問題・影響・修正案）/ やらないこと / 根拠の要求。

**向いている場合**

- コミット前の自己レビューや、PR のレビュー依頼。
- 複数ファイルにまたがる変更で、呼び出し元の漏れが心配なとき。

**向かない場合**

- コードの動作を説明してほしいだけ（task brief を使います）。

**例**

> 下書き: このコードに問題がないか見て

範囲（今回の PR の3ファイル、目的は注文 API への冪等性チェック追加）、観点（正しさ＞並行安全性＞性能＞可読性）、各指摘にファイル:行番号と修正案を付ける、といった依頼に書き換わります。

## Implementation task

**モード**: prompt · **グループ**: engineering

コーディングの依頼を、受け入れ条件・技術制約・インターフェース契約・境界と失敗時の扱い・成果物の形まで含む**タスク説明**にします。実装コードそのものは書きません。

**出力の形**: 目標と受け入れ条件 / 技術制約 / インターフェース / 境界と失敗 / 成果物 / 確認待ち。

**向いている場合**

- エージェントや同僚に中規模の変更を実装してもらう。
- 公開モジュールを触るので、先にインターフェースを決める必要がある。

**向かない場合**

- 探索的なプロトタイプで、書きながら方針を決めたいとき。

**例**

> 下書き: エクスポートを非同期ジョブにして、リクエストを止めないで

トリガー API、ジョブ状態の項目、ポーリングかコールバックか、同時実行の上限、再試行とタイムアウト、権限チェック、進捗の見せ方、合わせて直す呼び出し元まで書き出します。

## SQL query

**モード**: prompt · **グループ**: engineering

一言の集計依頼を、定義（期間・重複除去・NULL・単位）と性能制約まで含む SQL タスクにします。仮定は別に列挙させます。

**出力の形**: テーブルと列 / 定義（期間・重複・NULL・単位）/ 結果の要件 / 性能制約 / 権限と副作用 / 仮定一覧。

**向いている場合**

- レポートやダッシュボード用の集計。
- 「アクティブ」「継続率」などの定義が曖昧になりがちな依頼。

**向かない場合**

- 既存の SQL を説明してほしいだけ。

**例**

> 下書き: 先週のチャネル別の新規ユーザー数を出して

新規の定義（初回登録か初回購入か）、チャネルの列と重複除去キー、タイムゾーンと「先週」の範囲、テストアカウントの除外、並び順、スキャン対象と使えるインデックスまで補います。

## Test design

**モード**: prompt · **グループ**: engineering

テスト依頼を、正常・境界・異常・権限をカバーするケース表にします。優先度と自動化しやすいものも指定します。

**出力の形**: 対象とリスク / ケース表（番号・前提・手順・期待結果）/ カバレッジ / 優先度 / 自動化の提案。

**向いている場合**

- 新機能のリリース前にケースを補う。
- バグ修正後の回帰確認。

**向かない場合**

- 自動化スクリプトそのものが欲しいとき（下書きで明示した場合のみ）。

**例**

> 下書き: ログイン機能のテストケースを書いて

パスワード・SMS・外部ログインの3経路、失敗回数によるロック、空値・長すぎる値・記号、未確認メール、ロール別の見え方まで含め、番号と優先度を付けた表になります。

## Structured extraction

**モード**: prompt · **グループ**: structure

「この文章から項目を抜き出して」を、schema と欠損ルールを持つ抽出タスクにし、厳密な JSON だけを出力させます。

**出力の形**: 入力の形 / schema（項目・型・必須・列挙）/ 欠損と衝突の扱い / JSON のみ / 例。

**向いている場合**

- 契約書・メール・チケットを構造化データにする。
- 欠損は推測せず空にしてほしいとき。

**向かない場合**

- 要約や書き換えが目的のとき。

**例**

> 下書き: このメールから会社名・担当者・金額を抜き出して

会社名は本文か署名か、担当者に役職を含めるか、金額の通貨と税込/税抜、複数ある場合の優先、見つからない場合は null、出力は JSON のみ、まで定義します。

## Translation

**モード**: prompt · **グループ**: writing

翻訳依頼を、読み手・用語表・書式制約のあるローカライズタスクにします。大事なのは「動かしてはいけないもの」（製品名、項目名、プレースホルダー、Markdown 構造）です。

**出力の形**: 言語と地域 / 読み手とトーン / 用語表 / 書式 / 増減の禁止。

**向いている場合**

- 製品コピー、ヘルプ、メールの翻訳。
- `{{変数}}` やコードブロックを含む文書。

**向かない場合**

- 法的文書など、母語話者の監修が別に必要なもの。

**例**

> 下書き: これを日本語にして、顧客向けに

日本の企業顧客向けのビジネス文体、製品名と `{{user_name}}` は保持、見出し階層と箇条書きは維持、情報の追加・削除はせず訳文のみ、と指定します。

## Copy polish

**モード**: prompt · **グループ**: writing

推敲依頼を、どこまで変えてよいか・何を残すか・何を足さないかを明示した修正タスクにします。勝手な主張や例の追加、水増しを防ぎます。

**出力の形**: 文体と読み手 / 変更してよい階層 / 必ず残すもの / 禁止事項 / 全文＋変更点3つまで。

**向いている場合**

- 事実は問題ないが、読みにくい文章。
- 対外文書のトーンを揃えたいとき。

**向かない場合**

- 内容そのものに根拠が足りず、書き直しが必要なとき。

**例**

> 下書き: この段落をもっと正式にして

正式さの程度（対外告知か社内メールか）、段落順の変更可否、残す数字と結論、文の統合可否を確認し、末尾に主な変更点を挙げさせます。

## Grounded Q&A

**モード**: prompt · **グループ**: reasoning

「この資料に基づいて答えて」を、引用と「資料にない」の明示を伴う問答タスクにします。資料同士が矛盾する場合は、両方の出典を並べてから判断させます。

**出力の形**: 資料の範囲 / 引用の要求 / 未カバーの明示 / 矛盾の扱い / 出力構成（結論・根拠・未カバー）。

**向いている場合**

- 社内文書・規程・契約に基づく回答。
- 根拠をたどれる形で答案を残したいとき。

**向かない場合**

- 資料がなく、一般知識だけで答える場合。

**例**

> 下書き: この就業規則から年休の計算方法を答えて

規則のみを使い、条番号を引用、退職時の按分など書かれていない点は「未カバー」と明示、補足通知と矛盾する場合は両方の原文を挙げてから判断、という依頼になります。

## 自作テンプレート

テンプレートメニューの最後の項目が「自作テンプレートの新規作成」です。次の3つを入力します。

| 項目 | 役割 |
| --- | --- |
| 名前 | メニューに表示される名前（40文字まで） |
| 書き換えの指示 | どう書き換えてほしいか（2000文字まで） |
| 対象 | どんな下書きに向くかの一文（空でも可） |

自作テンプレートはこのブラウザの `localStorage` にだけ保存され、ブラウザのデータを消すと一緒に消えます。別のマシンに移すときや同僚と共有するときは、エディタの「JSON を書き出す」「JSON を読み込む」を使います。

## 選び方

| 状況 | テンプレート |
| --- | --- |
| 一文しかないが、完全なタスクにしたい | Task brief |
| 結果を他の人が受け入れる | Delivery contract |
| サンプルはあるが、書式が崩れるのが怖い | Worked examples |
| 多段の作業で、途中で迷いやすい | Reasoning steps |
| コードや PR をレビューしてほしい | Code review |
| 変更の実装を任せたい | Implementation task |
| 定義が曖昧になりがちな集計 | SQL query |
| 機能のテストケースを補いたい | Test design |
| 資料から決まった項目を抜きたい | Structured extraction |
| 翻訳・ローカライズしたい | Translation |
| 内容は良いが読みにくい | Copy polish |
| 資料に基づいて答えさせたい | Grounded Q&A |
| ほぼ満足で、少しだけ直したい | Incremental edit |

テンプレートは多ければよいというものではありません。同じ下書きでも、テンプレートを変えれば構造は目に見えて変わります。常用するものを1つ決めておき、仕事の性質が変わったときだけ切り替えてください。
