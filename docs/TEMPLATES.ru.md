# Шаблоны

[中文](./TEMPLATES.md) · [English](./TEMPLATES.en.md) · [Español](./TEMPLATES.es.md) · [Français](./TEMPLATES.fr.md) · [Deutsch](./TEMPLATES.de.md) · **Русский** · [日本語](./TEMPLATES.ja.md) · [Português (BR)](./TEMPLATES.pt.md)

В плагине пятнадцать шаблонов. Переключаются они в правом верхнем углу панели оптимизатора; переключение меняет **то, как переписывается черновик**, но никогда — сам черновик.

Каждый шаблон освещает свою грань одной и той же задачи:

- **Basic** — превратить одно предложение в полноценную задачу (Task brief, Role contract, Agent persona);
- **Structure** — вынести критерии приёмки или целевую схему вперёд (Delivery contract, Structured extraction);
- **Examples** — зафиксировать стиль и формат образцами (Worked examples);
- **Reasoning** — шаги с контрольными точками или ответ только по данному материалу (Reasoning steps, Grounded Q&A);
- **Engineering** — ревью кода, реализация, SQL и проектирование тестов;
- **Writing** — перевод и вычитка, где важно, насколько глубоко можно править;
- **Iterate** — минимальные правки поверх уже существующей версии (Incremental edit).

Последний пункт меню создаёт **свой шаблон**: ваша инструкция переписывания, хранится в этом браузере и переносится в JSON.

## Task brief

**Режим**: prompt · **Группа**: basic · **По умолчанию**

Универсальный вариант. Лучше всего подходит для черновиков, где есть цель, но нет деталей: «напиши мне что-нибудь», «глянь вот это».

**Структура вывода**: цель / известная информация / результат / ограничения / формат вывода. Пробелы помечаются как `待确认：…` («к уточнению»), а не заполняются выдуманными фактами.

**Когда использовать**

- черновик — одно предложение, но вы знаете, чего хотите;
- устную просьбу нужно превратить в задачу, которую выполнит другой человек;
- нужен промпт, который можно отправить, не дописывая контекст вручную.

**Когда не использовать**

- у требования уже есть жёсткие критерии приёмки (используйте Delivery contract);
- стиль важнее структуры и передать его можно только примерами (используйте Worked examples).

**Пример**

> Черновик: напиши анонс нашего нового релиза, выходит в пятницу, для существующих пользователей

Примерно превращается в:

```
Goal: a launch announcement for existing users about the release shipping this Friday.
Known: ships Friday; readers already use the product, so no from-scratch intro.
Deliverable: publishable Chinese note, under 300 characters.
Constraints: no overclaiming, no promises about unreleased features, no pricing.
Format: headline + three paragraphs + one call to action.
To confirm: what is the headline feature of this release?
```

## Delivery contract

**Режим**: prompt · **Группа**: structure

Ставит «что считается сделанным» на первое место. Подходит для работы, которую будут проверять не один раз: документация, отчёты, изменения в коде, чистка данных.

**Структура вывода**: задача / входные данные / спецификация вывода / критерии приёмки (3–6 проверяемых пунктов) / границы и исключения / запреты.

**Когда использовать**

- результат будет проверять кто-то другой;
- прошлые попытки возвращались на доработку, потому что стандарт нигде не был записан;
- модель должна спрашивать недостающие материалы, а не догадываться.

**Когда не использовать**

- задача исследовательская и стандарт ещё не определён;
- хватило бы просьбы в одну строку — контракт только утяжелит её.

**Пример**

> Черновик: преврати этот недельный отчёт в одностраничник для моего руководителя

Переписанная версия добавляет: какой отчёт считается входным, поля и порядок одностраничника, критерии приёмки (сначала вывод, каждое утверждение подкреплено цифрой, без нерасшифрованных аббревиатур) и что делать, если текст не влезает по длине.

## Worked examples

**Режим**: prompt · **Группа**: examples

Для случаев, когда два примера сильнее абзаца прилагательных. Модели гораздо лучше подражают формату, чем понимают «сделай профессионально».

**Структура вывода**: задача и область применения → 2–3 пары «вход → ожидаемый выход» → правила для входных данных вне примеров → пометка, что примеры иллюстративные.

**Когда использовать**

- формат строгий: колонки таблицы, тон текста, стиль кода;
- у вас уже есть два-три образца «пиши вот так»;
- важнее покрытие разных случаев, чем повторение одного и того же.

**Когда не использовать**

- в черновике не на что опереться для примеров — выдуманные примеры вводят в заблуждение;
- работа открытая и творческая.

## Reasoning steps

**Режим**: prompt · **Группа**: reasoning

Разбивает задачу на выполнимые шаги и указывает, где самопроверка, а куда откатываться при проблеме.

**Структура вывода**: переформулированная цель → 3–7 шагов (вход / действие / признак завершения) → контрольные точки → обработка сбоев → формат сдачи.

**Когда использовать**

- многошаговый анализ, отладка или сравнение вариантов;
- промежуточные результаты должен проверить человек;
- прошлые прогоны уходили не туда до самого конца.

**Когда не использовать**

- задача состоит из одного шага;
- работе нужна свободная креативность.

## Role contract

**Режим**: system prompt · **Группа**: basic

Превращает одну строку описания роли в системный промпт, которому агент может следовать долго. Панель пока не открывает системный режим; используйте `POST /prompt-optimize/optimize` с `optimizationMode: "system"`.

**Структура вывода**: идентичность / обязанности / рабочий процесс / границы / договорённость о выводе.

**Когда использовать**

- одна и та же роль используется в нескольких сессиях;
- роли нужны критерии суждения, а не только название.

**Когда не использовать**

- нужен разовый промпт под задачу.

## Agent persona

**Режим**: system prompt · **Группа**: basic

Пишет файл, который читается как живой человек: как он говорит, как решает, что предлагает сам, чего никогда не делает, плюс один пример ответа.

**Когда использовать**

- ассистенту нужны устойчивый голос и характер;
- нужна персона, а не должностная инструкция.

**Когда не использовать**

- формулировки о соответствии требованиям должны оставаться строгими — текст персоны этому мешает.

## Incremental edit

**Режим**: iterate · **Группа**: iterate

Применяет одно замечание к предыдущему результату, минимально его меняя: меняется только упомянутое, всё остальное сохраняется дословно.

**Структура вывода**: полный промпт (не diff). Если замечание противоречит тексту, побеждает замечание.

**Когда использовать**

- результат в целом верный, и нужно поправить тон, длину или один фрагмент;
- расплывчатое замечание вроде «сделай формальнее» нужно привязать к конкретному месту.

**Когда не использовать**

- направление неверное — новый прогон быстрее, чем правка по предложениям.

**Пример**

> Замечание: тон легче, а длинный список «к уточнению» свернуть в три строки

Меняются только формулировки, связанные с тоном, и этот список; заголовки, пунктуация и остальное остаются прежними.

## Code review

**Режим**: Prompt · **Группа**: Engineering

Превращает «глянь этот код» в ограниченное и приоритизированное ревью: зачем изменение, что смотреть первым и в каком формате отвечать.

**Выход**: охват / приоритеты / формат (важность, место, проблема, влияние, исправление) / вне охвата / доказательства.

**Подходит**: самопроверка перед коммитом; изменения в нескольких файлах, способные сломать вызовы.
**Не для**: объяснения, что делает код, или реализации исправления.

**Пример**

> Черновик: глянь этот код, что-то не так?

Станет: охват — три файла PR, добавляющего идемпотентность в checkout; приоритеты — корректность > конкурентность > производительность > читаемость; каждая находка ссылается на файл:строку; без переписывания файлов и споров о именах.

## Implementation task

**Режим**: Prompt · **Группа**: Engineering

Дополняет запрос по коду до инженерного брифа: цель и приёмка, технические ограничения, контракты интерфейсов, краевые случаи и форма сдачи. На выходе — **описание задачи**, а не код.

**Выход**: цель и приёмка / ограничения / интерфейсы / края и сбои / сдача / открытые вопросы.

**Подходит**: отдать среднее изменение агенту или коллеге; общие модули, где интерфейс согласуют заранее.
**Не для**: исследовательских прототипов, где решение рождается по ходу.

**Пример**

> Черновик: сделай экспорт асинхронным, чтобы не блокировать запрос

Станет: эндпоинт запуска, поле статуса, опрос или колбэк, предел параллелизма, ретраи и таймаут, проверка прав, показ прогресса и какие существующие вызовы надо менять.

## SQL query

**Режим**: Prompt · **Группа**: Engineering

Пишет запрос данных как SQL-задачу с явными определениями, полями и ограничениями по производительности и просит перечислить допущения отдельно.

**Выход**: таблицы и поля / определения (время, дубликаты, NULL, единицы) / форма результата / производительность / права / допущения.

**Подходит**: отчёты и разовые выгрузки; метрики с разными определениями (активные, удержание, GMV).
**Не для**: объяснения готового запроса или миграций схемы.

**Пример**

> Черновик: новые пользователи по каналам за прошлую неделю

Станет: определение нового пользователя, поле канала и ключ дедупликации, часовой пояс и точные границы недели, считать ли тестовые аккаунты, сортировка, допустимый диапазон сканирования и индекс.

## Test design

**Режим**: Prompt · **Группа**: Engineering

Пишет запрос на тесты как таблицу кейсов: обычный путь, границы, ошибки и права, с приоритетами и тем, что автоматизировать первым.

**Выход**: объект и риски / таблица (id, предусловия, шаги, ожидание) / покрытие / приоритет / автоматизация.

**Подходит**: дополнить кейсы перед релизом; убедиться, что исправление ничего не сломало.
**Не для**: просить скрипты напрямую, если черновик этого не требует.

**Пример**

> Черновик: напиши тест-кейсы для входа

Станет: пароль, SMS и сторонние входы отдельно; блокировка после N ошибок; пустое, очень длинное, спецсимволы; неподтверждённая почта; различия по ролям; каждый кейс с номером и приоритетом.

## Structured extraction

**Режим**: Prompt · **Группа**: Структура

Превращает «вытащи пару полей» в извлечение по схеме со строгим JSON и явными правилами для пропусков.

**Выход**: форма входа / схема (имя, тип, обязательность, enum) / правила пропусков и конфликтов / только JSON / один пример.

**Подходит**: договоры, письма, тикеты или страницы в данные; пакетные прогоны с загрузкой в базу.
**Не для**: пересказа или переписывания; картинок, которым нужен OCR.

**Пример**

> Черновик: достань компанию, контакт и сумму из этих писем

Станет: компания из тела или подписи, контакт с должностью или без, валюта и налоги суммы, какая сумма главная при нескольких, null если нет, только JSON.

## Translation

**Режим**: Prompt · **Группа**: Writing

Пишет запрос на перевод как задачу локализации с аудиторией, глоссарием и форматом. Главное — что не двигается: бренды, имена полей, плейсхолдеры, структура Markdown.

**Выход**: язык и регион / аудитория и тон / глоссарий / формат / без добавлений и сокращений.

**Подходит**: тексты продукта, справка и письма; конкретный рынок, где переписать лучше, чем переводить буквально; тексты с `{{переменными}}` и блоками кода.
**Не для**: юридических текстов, которым нужен человек.

**Пример**

> Черновик: переведи на японский для клиента

Станет: деловой японский для японского корпоративного клиента; сохранить названия продукта и `{{user_name}}`; сохранить заголовки и списки Markdown; ничего не добавлять и не убирать; только перевод.

## Copy polish

**Режим**: Prompt · **Группа**: Writing

Пишет запрос на вычитку как ограниченную правку: насколько глубоко можно менять, что сохранить и не расширять. Не даёт добавить тезисы, примеры или объём.

**Выход**: регистр и читатель / допустимая глубина / что сохранить / запреты / полный текст и до трёх заметок.

**Подходит**: факты в порядке, а текст не читается; единый голос в нескольких текстах.
**Не для**: материалов, которым не хватает аргументации.

**Пример**

> Черновик: сделай это более официальным

Станет: насколько официально (публичное объявление или внутреннее письмо), можно ли менять порядок абзацев, какие числа и выводы остаются дословно, можно ли объединять предложения, плюс список правок в конце.

## Grounded Q&A

**Режим**: Prompt · **Группа**: Рассуждение

Пишет «ответь по этим материалам» как задачу с цитатами и явным заявлением о непокрытом; при конфликте просит сначала перечислить источники, потом судить.

**Выход**: охват материала / правила цитирования / заявление о непокрытом / конфликты / структура (ответ, основания, пробелы).

**Подходит**: ответы по документации, политикам или договорам; ответы, которые должны быть прослеживаемы.
**Не для**: вопросов без материала для опоры.

**Пример**

> Черновик: как считаются отпуска по этому справочнику?

Станет: только справочник, с номерами пунктов; для отсутствующего — «не покрыто» (например, пересчёт при увольнении); если справочник и позднее уведомление расходятся, сначала процитировать оба, затем судить.

## Свои шаблоны

Последний пункт меню — «Новый свой шаблон», три поля:

| Поле | Назначение |
| --- | --- |
| Название | Показывается в меню; до 40 символов |
| Инструкция переписывания | Как переписывать; до 2000 символов |
| Для чего подходит | Одна строка о подходящих черновиках; необязательно |

Живут в `localStorage` этого браузера и исчезают вместе с данными сайта. Для переноса или передачи используйте экспорт и импорт JSON в редакторе.

## Как выбрать

| Ваша ситуация | Шаблон |
| --- | --- |
| Одна фраза, которую нужно развернуть в полноценную задачу | Task brief |
| Результат будет принимать кто-то другой | Delivery contract |
| Есть образцы и страх, что формат уплывёт | Worked examples |
| Многошаговая работа, которая любит уходить в сторону | Reasoning steps |
| В целом всё устраивает, нужна небольшая правка | Incremental edit |

Больше шаблонов — не лучше: один и тот же черновик под разными шаблонами даёт заметно разные структуры. Выберите один по умолчанию и переключайтесь, только когда меняется задача.
